### Organización Modular en Cuatro Capas

1. **Routers (`app/routers/`):** Controladores delgados con inyección `Depends(get_db)` y contratos de entrada validados en frontera mediante **Pydantic v2**.
2. **Servicios de Dominio (`app/services/`):** Lógica transaccional pura (`create_split`, `get_all`, `cambiar_propietario`) encapsulando `db.commit()` y `db.rollback()`.
3. **Presentación SSR (`templates/` y `static/js/`):** Jinja2 para renderizado inicial e interacciones reactivas nativas con Vanilla JS y API `fetch`.
4. **Persistencia (`app/models/`):** Tipado declarativo en SQLAlchemy 2.0 (`Mapped[...]`), neutral respecto al motor relacional subyacente.

## 04. Desafíos de Ingeniería & Casos Límite

El desarrollo resolvió fricciones críticas que abarcan desde la reactividad en el frontend del navegador hasta la consistencia transaccional en el motor relacional:

### Reto 1: Búsqueda Reactiva con Debounce y Cancelación en Vuelo (Vanilla JS ES6+)

En el patio operativo, las búsquedas continuas por placa o estatus podían generar ráfagas de peticiones desordenadas. Para garantizar una respuesta instantánea sin sobrecargar el servidor ni provocar condiciones de carrera en el DOM (*race conditions*), se implementó un controlador de búsqueda reactiva con **debounce de 250 ms** y descarte de solicitudes obsoletas mediante **`AbortController`**:

```javascript
/**
 * static/js/ordenes_search.js
 * Búsqueda reactiva con debounce nativo (250 ms) y cancelación de peticiones en vuelo.
 */
(() => {
  const searchInput = document.getElementById("ordenes-search-input");
  const tableBody = document.getElementById("ordenes-table-body");
  const countBadge = document.getElementById("ordenes-count-badge");
  let debounceTimer = null;
  let activeController = null;

  if (!searchInput || !tableBody) return;

  searchInput.addEventListener("input", (e) => {
    const query = e.target.value.trim();
    clearTimeout(debounceTimer);

    debounceTimer = setTimeout(async () => {
      // 1. Cancelar cualquier petición previa aún en tránsito
      if (activeController) {
        activeController.abort();
      }
      activeController = new AbortController();

      try {
        const url = `/api/ordenes?q=${encodeURIComponent(query)}`;
        const res = await fetch(url, { signal: activeController.signal });

        if (!res.ok) throw new Error(`HTTP error ${res.status}`);
        const data = await res.json();

        // 2. Renderizado reactivo sin recarga de página (< 35 ms)
        renderOrders(data.ordenes);
        if (countBadge) countBadge.textContent = `${data.total} órdenes`;
      } catch (err) {
        if (err.name !== "AbortError") {
          console.error("Error al buscar órdenes:", err);
        }
      } finally {
        activeController = null;
      }
    }, 250);
  });

  function renderOrders(ordenes) {
    tableBody.innerHTML = ordenes.map(o => `
      <tr class="hover:bg-neutral-800/40 transition-colors" data-id="${o.id_orden}">
        <td class="font-mono text-emerald-400 font-semibold">${o.numero_impreso || 'S/N'}</td>
        <td class="font-mono">${o.placa_vehiculo}</td>
        <td>${o.cliente_nombre || 'Desconocido'}</td>
        <td><span class="badge badge-${o.estatus.toLowerCase()}">${o.estatus}</span></td>
        <td class="text-right font-mono">$${Number(o.total_orden).toFixed(2)}</td>
      </tr>
    `).join("");
  }
})();
```

### Reto 2: Particionamiento Atómico por Límite de Papelería (`create_split`)

Los talonarios preimpresos disponen de cupos inalterables: 10 renglones útiles en Facturas y 12 en Notas de Entrega. # Reserva atómica de N correlativos continuos bajo bloqueo pesimista
seq = (
    db.query(models.DocumentSequence)
    .filter(models.DocumentSequence.tipo_documento == data.tipo_documento)
    .with_for_update()
    .first()

base_numero = seq.ultimo_numero + 1
seq.ultimo_numero += chunks_count  # Reserva del bloque continuo
db.flush()

for i, chunk in enumerate(items_chunks):

### Reto 3: El Patrón Snapshot Histórico (Desnormalización Deliberada vs. 3NF)

En un esquema 3NF estricto, una consulta a una orden lee el cliente mediante `Orden -> Vehiculo -> Cliente`. Si el vehículo cambia de dueño, el historial fiscal de años pasados mutaría. Para blindar la auditoría tributaria, la cabecera congela las columnas `cli_nombre`, `cli_rif` y `veh_modelo` en el instante de la emisión, exponiendo propiedades ORM de respaldo transparente:

@property
def cliente_nombre(self) -> str | None:
    # 1. Prioridad: Snapshot inmutable congelado al momento de emitir la orden
    if self.cli_nombre:
        return self.cli_nombre
    # 2. Respaldo histórico: Relación viva con el titular actual del vehículo
    if self.vehiculo and self.vehiculo.cliente:

    return None

### Reto 4: Resiliencia de Persistencia y Locking en Hosting cPanel (`PRAGMA journal_mode=DELETE`)

En cPanel y Phusion Passenger, el modo SQLite WAL (*Write-Ahead Logging*) genera bloqueos huérfanos (`database is locked`) cuando los procesos se reciclan agresivamente por inactividad. Se interceptó la conexión mediante eventos de SQLAlchemy para fijar el modo tradicional `DELETE`, obteniendo un archivo único `.db` 100% autocontenido y apto para respaldos automáticos en caliente:

## 05. Spec-Driven Development (v1 MVP a v2.0 Clean Architecture)

La evolución técnica de la plataforma ilustra el ciclo de vida de refactorización guiado por especificaciones (**SDD**), eliminando de raíz la deuda técnica acumulada durante el MVP:

### Matriz Comparativa de Deuda Técnica

| Dimensión Arquitectónica | Estado Anterior (v1 — MVP Monolítico) | Estado Final Refactorizado (v2.0) |
| :--- | :--- | :--- |
| **Estructura de Código** | Lógica de negocio y consultas SQL mezcladas en rutas HTTP. | **Service Layer:** Controladores delgados y servicios de dominio en `app/services/`. |
| **Eficiencia de Base de Datos** | **Problema N+1 Severo:** Consultas individuales por cliente, vehículo y técnico. | **Eager Loading Estratégico:** Reducción a **1 sola consulta SQL** mediante precarga `joinedload`. |
| **Modelado de Personal** | Texto plano desnormalizado `mecanico_responsable: str`. | **Relación Many-to-Many Estricta:** Tabla `orden_mecanicos` con claves e índices compuestos. |
| **Métricas y Analítica** | Cómputo de comisiones mediante bucles `for` en memoria Python. | **Agregaciones SQL Nativas:** Sentencias `CASE WHEN` calculadas en base de datos en `< 20 ms`. |

### Erradicación del Problema N+1 mediante `joinedload` Multinivel

En la versión inicial, renderizar 100 órdenes disparaba **301 consultas a la base de datos** ($1 + 3N$). En v2.0, el servicio reescribe la consulta instruyendo al ORM a precargar relaciones mediante `LEFT OUTER JOIN`:

  <div class="whitepaper-code-header">
    <div class="whitepaper-code-dots">

```python
q = (
    db.query(models.Orden)
    .options(
        joinedload(models.Orden.vehiculo).joinedload(models.Vehiculo.cliente),
        joinedload(models.Orden.mecanicos).joinedload(models.OrdenMecanico.mecanico),
    )
    .outerjoin(models.Vehiculo, models.Orden.placa_vehiculo == models.Vehiculo.placa)
    .outerjoin(models.Cliente, models.Vehiculo.id_cliente == models.Cliente.id_cliente)
    .filter(models.Orden.activo == True)
)
```

**Impacto:** Reducción de 301 consultas a **1 única sentencia SQL consolidada**, disminuyendo la latencia de carga en más de un **85%** (< 15 ms en producción).

### Cómputo Analítico en Base de Datos con Agregaciones `CASE WHEN`

En lugar de transferir registros a Python para bucles en memoria, `/api/mecanicos/stats/resumen` delega el cálculo completo al motor relacional mediante expresiones condicionales `CASE WHEN`:

<div class="whitepaper-code-window">
  <div class="whitepaper-code-header">
    <div class="whitepaper-code-dots">
      <span class="whitepaper-code-dot whitepaper-code-dot-close"></span>
      <span class="whitepaper-code-dot whitepaper-code-dot-minimize"></span>
      <span class="whitepaper-code-dot whitepaper-code-dot-maximize"></span>

```python
stmt = (
    select(
        models.Mecanico.id_mecanico,
        models.Mecanico.nombre,
        func.sum(case((models.Orden.tipo_documento.in_(REALES), 1), else_=0)).label("total"),
        func.coalesce(func.sum(case(
            (models.Orden.tipo_documento.in_(REALES) &
             (models.OrdenDetalle.tipo_item == "mano_de_obra"),
             models.OrdenDetalle.cantidad * models.OrdenDetalle.precio_unitario), else_=0
        )), 0).label("monto_total"),
        func.sum(case(
            (models.Orden.tipo_documento.in_(REALES) &
             (models.Orden.estatus.in_(["Procesado", "Completado"]), 1), else_=0
        )).label("completadas"),
    )
    .outerjoin(models.OrdenMecanico, models.Mecanico.id_mecanico == models.OrdenMecanico.id_mecanico)
    .outerjoin(models.Orden, (models.OrdenMecanico.id_orden == models.Orden.id_orden) & (models.Orden.activo == True))
    .outerjoin(models.OrdenDetalle, models.OrdenDetalle.id_orden == models.Orden.id_orden)
    .filter(models.Mecanico.activo == True)
    .group_by(models.Mecanico.id_mecanico)
)
```

</div>

**Impacto:** Cálculo estadístico consolidado resuelto en **`< 20 ms`**, liberando completamente la CPU del hilo web y habilitando auditorías inmediatas sin degradar la navegación concurrente.

## 07. Conclusiones y Retrospectiva de Ingeniería

El despliegue de **Taller-Admin v2.0** valida principios clave de ingeniería para sistemas transaccionales en contextos operativos reales:

1. **Monolito SSR Pragmático (YAGNI):** Jinja2 y Vanilla JS ES6+ resolvieron la operativa sin pipelines de empaquetado ni dependencias de npm complejas, operando con menos de **80 MB de memoria RAM** e impresión física milimétrica.
2. **Rescate de Negocios Legados:** El datastore híbrido salvó 8 años de historial en un almacén frío JSON inmutable, sentando en simultáneo las bases de un núcleo relacional limpio en 3NF.
3. **Resolución de Restricciones del Mundo Real:** Bloqueos pesimistas para papel continuo preimpreso, snapshots inmutables para blindaje tributario y configuración de motor adaptada a hosting compartido.
4. **Madurez Arquitectónica (SDD):** El ciclo de vida guiado por especificaciones permitió validar primero el producto con usuarios y refactorizar posteriormente la arquitectura hacia capas de servicios desacopladas y latencias de base de datos inferiores a **15 ms**.
